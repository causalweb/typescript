# Implementation and conformance report

Status: Experimental source preview; no full deployment conformance claim

The [Linux and Windows checks on source commit `954fc45c395a2a884bb4ca8926212fd63ede9dbf`](https://github.com/causalweb/typescript/actions/runs/39115673867) passed all six selected pinned runner profiles, the package consumer, demo, release checks, and the historical peer job. These are commit-bound checks, not a class certification or interoperability evidence for the proposed URI rule.

The current preview pins runner `4284bf951ee8de65991e2e415ecd9f27109dc69d`. Its workflow additionally runs the one-case `http-redirect-agent-v1` profile against the pinned specification and the four-case `uri-identities-draft-v1` profile against proposal commit `b5a216510708553f7ac763d02ec12755df78d7f1`. The latter has a separate proposal pin and is not part of the normative revision or historical Rust peer claim. The runner checks the redirect using two controlled loopback origins; TypeScript also has direct adapter tests. These additions do not certify browser, proxy, or deployment behavior.

The order-source/view reference has a separate class-specific evidence matrix at `reference/CLASS_REPORT.md` in the source checkout. It records which SDK runner profiles pass locally and why the reference application does not yet claim any deployment conformance class.

The normative input is draft `0.1.1-experimental`, with exact source, peer, and runner pins in [SPEC_REVISION](SPEC_REVISION), [RUST_REVISION](RUST_REVISION), and [CONFORMANCE_REVISION](CONFORMANCE_REVISION). Shared vector revision: `0.1.4`.

An unreleased TypeScript preview also enforces the proposed fragment-free RFC 3986 identity rule. Its consumer passes all four complete signed cases in the source checkout's `test/vectors/uri-identities.json`, copied byte-for-byte from the proposal commit above, alongside local signed/parser tests. The fourth case rejects a signed lowercase issuer when only an uppercase-scheme issuer is trusted. The historical Rust peer and published specification revision do not cover these cases. They are not part of the pinned conformance claim above; see [migration guidance](MIGRATION.md).

The repository also provides development-only adapters for the separate [`causalweb/conformance`](https://github.com/causalweb/conformance) runner. The JSON Lines adapter supports the 32-case `evidence-verification-v1`, 17-case `prefix-evaluation-v1`, three-case `context-reduction-v1`, 11-case `http-client-confirmation-v1`, and 15-case `http-observer-v1` profiles. A separate loopback test server supports the 7-case `http-transport-server-v1` profile using the public Node header conversion, observer, and response-writing helpers. The response/parser profile excludes cross-origin redirect forwarding; the separate runner-controlled `http-redirect-agent-v1` profile exercises that behavior through the actual Fetch client. The proposal-only URI profile uses the same evidence-verification adapter contract with case-scoped issuer trust. The observer profile uses ephemeral test evidence and synthetic fixed-cut snapshots. The transport profile is raw loopback HTTP/1.1 only; it does not establish a generic server, TLS, proxy, storage-adapter, or deployment claim. The adapters expose only public profile outcomes and do not expose local diagnostics.

## Evidence obtained

- All six baseline JWS, 26 security, twenty prefix/composition, and twelve HTTP outcome fixtures pass through this implementation's own code. The shared runner independently invokes this engine for 32 evidence-verification cases and 17 selected prefix-evaluation cases.
- The context-reduction adapter uses the public carrier helper over independently signed evidence. It returns only indices into the original ordered evidence list; the runner checks the three Prefix Profile reduction vectors, including a shorter-lived higher position and independent domains.
- Native Node.js cryptography supplies ES256; no Rust engine, FFI, subprocess, or shared protocol implementation is used by the library.
- The development peer check parses each implementation's actual field strings and signed evidence in both directions. It checks stale/covered state, expiration, forgery, and subject mismatch with synthetic snapshots. On Linux, it also invokes Rust's POSIX-only local source fixture: a source fact is persisted before issuance, an injected interruption leaves a recoverable blank outbox entry, and TypeScript independently validates both issued and recovered evidence. The same peer starts its constrained-observation endpoint and a deliberately limited Rust loopback HTTP source, observes a genuine stale response, verifies the delivered token before advancing its persistent projection document, then confirms the observation. It also starts a TypeScript source process and Rust observer process with separate persisted documents: TypeScript terminates after a source/outbox replacement and recovers the blank outbox entry; Rust terminates after a projection/frontier replacement and reconstructs the covered state; delayed, duplicate, out-of-order, forged, and recovered deliveries are exercised across their HTTP boundary.
- Real loopback HTTP tests exercise the public client/observer interfaces, reject an unaware 200, avoid cross-origin redirect forwarding, validate failure order, enforce a problem-body limit, and cancel an interrupted exchange.
- A persistent local-service experiment uses separate source/projection directories and HTTP services. It keeps response bytes and a prefix frontier in one atomically replaced document, reports an actual stale causal failure before delivery, and confirms after delivery. It covers out-of-order and duplicate delivery, a modified token, logical service reconstruction, and an injected interruption after durable source commit followed by outbox recovery.
- A separate SQLite experiment runs source and observer as local processes with independent transactional databases. It demonstrates source and observer interruption/restart recovery, pre-commit delivery rollback, stale-to-confirmed constrained observations, bounded authenticated test delivery, and explicit self-signed TLS test trust. It is still a fixed-clock, single-host test harness rather than a reusable storage adapter or deployment profile.
- The order-service reference uses operator-supplied TLS/key paths, separate SQLite databases, and a process-local delivery credential. A local test forcibly terminates the source after evidence issuance while the view is unavailable, restarts it to drain the durable outbox (including expired undelivered evidence), then forcibly terminates the view after a confirmed read and confirms the same state-bound result after restart. It also restarts both roles with a new active signing key and a view keyring containing old and new public keys; old unexpired and new evidence both confirm. A store test treats an expired reissue for the same stable fact as an idempotent duplicate even if an earlier delivery was applied but its acknowledgement was lost, while rejecting a changed fact. This is process-termination and local key-rotation evidence, not a power-loss, external deployment, or full conformance claim.
- The reference HTTPS test also rejects malformed UTF-8 and oversized JSON before the first source position is committed. Restarting the view with a changed application credential denies the old credential without a causal result while the newly authorized request confirms the same evidence. This is a local rotation check, not a live policy-update or concurrent authorization-race proof.
- The one-command local quickstart runs the source and view as separate HTTPS processes with separate disposable SQLite files. It observes a stale constrained read before delivery, then confirms through the public SDK client after authenticated delivery; the workflow is now a CI step on Linux and Windows. Its bundled localhost certificate and generated temporary secrets are test-only. It does not prove an operator-supplied-certificate deployment or an external developer's usability result.
- The reference fault model at `reference/FAULT_MODEL.md` in the source checkout maps process interruptions, evidence refresh, keyed client-write retries, view lineage loss, key and credential changes, and paired backup recovery to specific tests. It also records that a retry with a new key or a pre-upgrade write can still duplicate an intended operation; terminal failure is a manual operator decision rather than an automatic incident diagnosis; and hard-bounded shutdown, power-loss durability, and external operator restoration still lack proof.
- A local HTTPS test holds the delivery response open, sends `SIGTERM` to the source, checks prompt exit with the outbox entry still pending, then restarts the source and confirms the preserved fact. Shutdown now aborts outbound Fetch, drains active handlers and the delivery job before closing SQLite, and closes remaining HTTP sockets after ten seconds. This does not bound a blocked synchronous SQLite operation or establish power-loss durability.
- A reproducible resource measurement at `reference/MEASUREMENTS.md` in the source checkout covers single-process SQLite source commit, ES256 issuance/verification, and view application for 100–2000 orders on one Windows/Node host. It records time, sampled RSS, and database sizes and exposes the growing cost of the view's full-lineage scan. That storage-path sample alone is not a two-service HTTP test or a capacity claim.
- The same measurement report now includes a two-process localhost HTTPS mode: 100–500 sequential application writes, authenticated asynchronous delivery, and a final constrained read that confirms every order. It records submission and confirmation time plus write-latency percentiles. One-off samples with a test certificate and no concurrency, child-process RSS, or sustained-load window are not production sizing evidence.
- The view's delivery path now streams positions while validating the entire applied prefix, avoiding allocation of representation rows it does not use. A same-row-count gap test still yields `unknown`; a repeat local resource sample shows lower observed RSS at 2000 orders but similar apply time. No schema migration or constant-time lineage check is claimed.
- The order-service HTTPS test signs a valid application delivery envelope around forged causal evidence. The view rejects it with a marker-free `400` before state mutation; a malformed event receives the same input classification, and expired client evidence yields an `expired` item outcome inside the ordinary aggregate `unsatisfied` result. The application envelope and causal evidence are therefore checked independently in this local reference path.
- A separate quiescent backup exercise uses SQLite's backup API for both databases, rejects a source/view pair with incompatible deployment identities or stable facts, checks database integrity and a checksum manifest, restores into new paths, and resumes a pending view event without moving the frontier ahead of state. Each reference database now persists its role, issuer, domain, audience, and principal, refusing reuse under changed configuration or silent rebinding of populated legacy data. This cannot detect externally issued evidence after the backup cut and is not a continuous-backup or disaster-recovery claim.
- Additional tests cover nested/escaped duplicate names, invalid UTF-8, exact integral NumericDates, Unicode scalar handling, URI syntax without normalization, empty/missing limits, control characters, expiry after reading, and access changes.

The source suite includes tests for retained local adapter causes, both authorization checkpoints, clock errors, snapshot-contract errors, rejection of non-byte JavaScript bodies, safe HTTP conversion, runtime-private issuer configuration, and persistent local-service and SQLite behavior. Real HTTP tests retain the local cause while returning empty ordinary 503 responses. A separate package check installs the actual `.tgz` into a temporary application, compiles with strict Node-only types, checks invalid API uses at compile time, and exercises stale/covered/denied observations and the public error API. The committed CI workflow tests Node.js on Linux and Windows and runs a separate pinned-Rust peer job. A workflow is not evidence that CI passed; refer to the run on the reviewed commit.

## Policies and assumptions

The only configured algorithm is ES256. Unknown protected-header parameters are rejected by local policy. Trust contains exact issuer strings, per-issuer key IDs and domain authority, audience, positive maximum lifetime, and non-negative skew. The subject is exact-matched to the already authenticated application partition. Keys and domain sets are copied on construction; no key URL in evidence is followed.

Positions and dates use exact arithmetic. Unknown authenticated profiles keep their position opaque and yield `unsupported` after expiry precedence. Numeric frontiers cover every relevant component; unknown lineage blocks a positive claim. Exclusions are trusted adapter statements bound to the snapshot's versioned contract/schema and a position interval.

No server-side deliberate progress waiting, online revocation lookup, or background key discovery is implemented. The portable client offers signal-bounded polling for retryable `unsatisfied` GET observations, without a progress guarantee. `retainedContextIndices` performs the optional Prefix Profile carrier reduction only after the caller has verified each input under current policy. It returns indices into the caller's original token list, preserves order, and retains any item it cannot safely omit; callers must never synthesize a replacement token. Policy must be current at request time and remain authorized through response commitment. Do not cache verified evidence across revocation or authorization changes.

## Not yet claimed

The test-only local-file and SQLite experiments exercise an outbox-shaped source record, source-order recovery, and a representation/lineage transaction. They do not provide reusable database/outbox adapters, durable signing-key storage, an fsync protocol, an operating-system or power-loss crash campaign, multi-host deployment evidence, or the required database and load tests. `Snapshot` cannot prove that a caller used a real transaction. HTTP helpers do not by themselves establish a complete deployment's TLS, browser, proxy, cancellation, authorization, or conditional-request behavior.

Generic identifier grammar and JSON edge cases still need cross-runtime review, especially URI scheme syntax versus exact identity comparison and lone Unicode escapes. The fragment-free identity rule has been selected and implemented in the unreleased TypeScript preview, but is not yet pinned or interoperable with historical Rust. Both implementations preserve exact identity strings; neither may treat normalization as new issuer/domain authority. These questions block stability, not further experimentation.

The portable TypeScript Fetch client transports opaque evidence in browser-capable runtimes, but browser issuance, verification, key management, CORS integration, and deployment certification are not claimed. No external pilot, independent security audit, exhaustive conformance coverage, comprehensive fuzzing, or production-readiness certification is claimed. Independent protocol engines written by the founding author are not independent external review. The Rust fixture has only a bounded loopback-test HTTP parser; it has no transactional store, `fsync`, durable key store, TLS, authenticated delivery, concurrency control, or Windows persistence path. The TypeScript source and projection are test harnesses, not reusable adapters. The cross-runtime experiment gives bounded persistent-service evidence, but a production deployment class remains a separate release gate.
