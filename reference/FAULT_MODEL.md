# Order reference fault model

Status: local process and SQLite evidence, not a production durability or conformance claim. This document describes the [order source/view reference](README.md), not every application of the protocol. The two roles run on one host with separate SQLite databases in WAL mode and `synchronous = FULL`. Each process has one synchronous database connection. HTTPS, credentials, key files, and storage are operator supplied outside the local demo.

## What must remain true

- A source position names one committed fact. The source order row and its recoverable outbox state commit in one SQLite transaction. Evidence is issued only after that commit. A response with `Causal-Context` is never written before evidence has been stored.
- The view verifies delivery authorization, its signed envelope, and causal evidence before a projection write. It applies contiguous positions only, and writes representation rows and their frontier in the same transaction. A constrained read selects both in one transaction.
- A view that cannot establish its applied contiguous lineage reports `unknown`, never `satisfied`. An ordinary authentication or local error carries no causal success marker.
- Source and view database identities (role, issuer, domain, audience, subject, schema version) must agree with configured identity. A populated unbound database is not silently adopted.
- Only a view-operator decision stored for this projection contract and an authenticated pending position may cause a `failed` outcome. The observer reads that decision with the representation and frontier in one SQLite transaction. A source claim, retry count, or delivery error does not record it.

These invariants depend on SQLite and the host filesystem honoring their documented transaction and durability behavior. They do not prove survival of a device, filesystem, or power failure.

## Failure points and expected response

| Interruption or fault | Expected state and recovery | Local evidence |
| --- | --- | --- |
| After the source fact insert but before its transaction commits | SQLite rolls back the source row; the next position remains one, the request-key map stays empty, and no evidence is visible. Retrying the same request key may then create the first committed fact. | [Process test](service.test.mjs) kills the source inside its transaction, reopens the database, and retries; this is not a power-loss test. |
| After source commit, before evidence is stored | A blank outbox row retains the stable fact and position. Source restart signs that row, then retries delivery. The interrupted HTTP request does not receive causal evidence. | [service test](service.test.mjs) kills immediately after the commit and verifies the blank row and delivered recovery; [store test](order-store.test.mjs) covers reopening it |
| Client retries a write after an uncertain response | The same application request key and order return the original fact and position. A conflicting order gets marker-free `409`; an expired token is reissued for the same fact. A different key means a new intended operation. | [service test](service.test.mjs), [store test](order-store.test.mjs) |
| Two source processes contend for the same SQLite writer lock | A bounded two-second lock wait lets both keyed commits serialize after a short competing transaction; the same key returns the same fact and a distinct key advances once. Longer lock contention can still fail as an ordinary local error, without issuing evidence for an uncommitted fact. | [two-process source test](source-concurrency.test.mjs) holds an external `BEGIN IMMEDIATE` lock, then exercises two real child-process writers against the same database |
| After evidence is stored or returned, before delivery acknowledgement | The source retries the same fact. While the view lags, a constrained read is `unsatisfied` rather than an unaware success. A `SIGTERM` during a stalled outbound delivery aborts that fetch, leaves the fact pending, and permits retry after restart. | [service test](service.test.mjs), [local quickstart](quickstart.mjs) |
| View rejects the delivery credential | The source logs the HTTP status when the failure reason changes and keeps the outbox entry pending. An operator must correct the credential; after a source restart with the matching credential, delivery resumes for the same fact. Repeated identical failures do not produce one log line per retry. | [service test](service.test.mjs) observes `401`, inspects the pending row, and confirms the same evidence after correction |
| Evidence expires while its fact remains undelivered | The source issues fresh evidence for the same fact and position. A view that had committed an earlier delivery but lost its acknowledgement accepts the refreshed delivery as an idempotent duplicate; changed facts are rejected. Already-issued client evidence is not refreshed. | [store test](order-store.test.mjs), [service test](service.test.mjs) |
| Operator replays acknowledged history to a fresh contract-bound view | With the source stopped, replay sends committed positions in order through the authenticated delivery path. Expired or blank stored evidence is reissued for the same fact. A rejected delivery stops the run; rerunning from the start is idempotent and does not reset source acknowledgement flags. | [replay test](replay.test.mjs) uses live HTTPS and a new view database; it does not prove an external cutover or concurrent-source exclusion |
| Delivery arrives out of order or is repeated | A later position waits pending. A matching duplicate is a no-op; a conflicting fact for that position is rejected. A bearer credential alone, an invalid delivery signature, a valid delivery signature wrapping forged causal evidence, or a signed envelope whose issuance time disagrees with its causal evidence cannot mutate the view. | [store test](order-store.test.mjs), [service test](service.test.mjs) |
| View stops before or after its projection commit | SQLite rolls back an incomplete transaction. A committed row and frontier survive together; a restarted view selects the same state-bound cut. Lost or noncontiguous applied rows make the frontier `unknown` and stop further delivery pending repair. | [service test](service.test.mjs) kills after a projection row write but before its frontier update, then after transaction commit but before acknowledgement; restart verifies rollback, atomic durability, and duplicate replay. [Store test](order-store.test.mjs) checks damaged lineage. |
| Application credential changes | After a view restart with the new credential, the old credential gets an ordinary marker-free `401`; valid evidence alone grants no access. | [service test](service.test.mjs) |
| View operator records or resolves terminal failure | An append-only decision survives restart and paired backup/restore. An uncovered affected position returns HTTPS `503` with a `failed` problem outcome; an earlier position remains stale, and an accounted position is satisfied. Wrong deployment identity or a position with no authenticated pending event is rejected. Two separate tenant-bound view databases retain distinct outcomes for the same issuer, domain, and position after restart; this is not a shared multi-tenant storage proof. A separate operator process commits recording and resolution between frontier and failure-history reads; each in-flight snapshot retains its original cut, and the next read sees the change. | [operator test](operator.test.mjs), [HTTPS service test](service.test.mjs), [backup test](backup.test.mjs) |
| Source signing key rotates | The view keyring must contain both old and new verification keys during the overlap. The services restart with the new active key; old unexpired evidence and new evidence can both confirm. This is not live or coordinated rotation. | [service test](service.test.mjs) |
| Request exceeds 16 KiB or has malformed UTF-8/JSON | The shared request parser rejects it before a source position is committed or a delivery is applied. Malformed delivery dates are also invalid input, not a local server failure. | [service test](service.test.mjs) exercises malformed UTF-8/JSON and oversized bodies on both POST routes plus malformed view-delivery dates; the view remains stale and responses carry no causal marker |
| Source and view are restored from a backup | The quiescent pair must pass checksums, integrity checks, identity and history agreement, and frontier consistency. A restored pending event remains recoverable. | [backup test](backup.test.mjs) |

## Operator recovery rules

1. Stop both processes and prevent new client writes before backup, restore, or manual inspection. Preserve the SQLite database, WAL, and SHM files together until the services are stopped; never copy only a live `.sqlite` file. Use the [paired backup tool](README.md#paired-backup-and-restore-exercise) for a quiescent snapshot.
2. Keep the source database as the authority for stable facts and positions. Do not delete or reassign an outbox position to silence retries. On restart, the source reissues expired *undelivered* evidence and drains its outbox.
3. If a view reports `unknown` or rejects delivery because lineage is damaged, stop serving confirmed reads. Restore a verified matching pair, or rebuild a new view from the complete authoritative source history under a reviewed procedure. Do not manually advance the frontier.
4. Before restoring an older source snapshot, determine whether later evidence could have escaped to any client or peer. If that cannot be ruled out, restoring under the same source-domain identity is unsafe. Recover the latest history or use a reviewed domain rollover and projection repair. The checksum manifest does not answer this question.
5. Protect the signing key, TLS material, bearer credentials, databases, and backups under operator controls. The backup tool does not package or authenticate secrets, and its checksum manifest is not a signature against a malicious writer.

## Gaps before a deployment claim

The test-only `CW_TEST_FAULT_POINT` setting is honored only with `NODE_ENV=test` and kills the child at `before-source-commit`, `after-source-commit`, `before-frontier`, or `after-view-commit`. Do not set these in a deployed service. SQLite writes the projection row and frontier in one transaction, so there is no state in which the row is independently durable before the frontier; the two view process-kill points bracket this atomic commit, not a power-loss test.

The source requires an application request key and maps it atomically to one stable fact. Reusing that key with the same order after a lost response returns the original fact; using a new key for the retry can still create a duplicate, and pre-upgrade requests have no mapping. This is not a cross-service exactly-once guarantee. The two-process writer test covers one short artificial lock collision, not sustained concurrent load or a multi-replica source deployment. Terminal failure is a manual view-operator assertion over an authenticated pending record; these tests do not prove that a real-world incident is irreparable or that an external operator can diagnose one correctly. The OS username in the history is a label, not an authentication mechanism. There is no general online schema migration, certified resource bound, continuous backup, multi-host failover, coordinated key rotation, power-loss campaign, or independent external operator exercise. On `SIGTERM`, the server stops accepting connections, aborts outbound delivery, allows active requests up to ten seconds before closing their sockets, waits for their handlers and delivery job, then closes SQLite. The local test shows prompt exit during one stalled delivery and persistence of its outbox record; it is not a hard real-time bound if a synchronous database operation blocks the event loop. Existing unit and process tests do not close those gaps.
